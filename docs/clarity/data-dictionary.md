# Clarity Source Data Dictionary

The user approved this synthetic source model. Column definitions below are exported from the local design; this is not a proprietary Epic specification.

> Population decision: generate both sources independently with shared synthetic identities. Earlier Clarity-to-Caboodle ETL language below is historical mapping context, not an instruction to build that ETL. Source-to-Bronze reconciliation is performed independently for each source.

**Proposed entities:**

| Entity | Description |
| --- | --- |
| Patient | Demographics and patient identifiers |
| Encounter | Visits, admissions, and encounters |
| Provider | Clinical providers |
| Department | Clinical and hospital departments |
| Diagnosis | Encounter diagnoses |
| Procedure | Clinical procedures |
| Medication | Medication orders |
| Medication Administration | Medication administration events |
| Laboratory Order | Lab requests |
| Laboratory Result | Lab observations and results |
| Vital Signs | Patient observations |
| Coverage | Insurance coverage |
| Appointment | Scheduled care visits |

**Model requirements:**

- Define primary keys, foreign keys, cardinality, and relational constraints.
- Specify realistic data types and nullable fields.
- Include created/modified timestamps and operational status fields where appropriate.
- Define natural/business identifiers and relationships across patient, encounter, provider, and clinical events.
- Identify columns suitable for incremental ingestion and any limitations for deletes.

##### Data Dictionary Conventions

The following is a proposed synthetic operational schema, not an Epic schema specification. All tables reside in `dbo` in the Clarity simulation database. `PK` means primary key; `FK` means foreign key; `UQ` means unique constraint. `Nullable = No` means `NOT NULL`. IDs are immutable `bigint` values generated by the simulator; business codes remain separate from database keys.

All event timestamps use UTC and `datetime2(7)`. Date-only values use `date`. Quantities use fixed-precision decimals, not floating-point values. Status and code fields use documented, validated value sets. Names and descriptions use Unicode text. Values, lengths, and code sets remain subject to model approval.

**Shared columns on every Clarity table:** These columns are part of each table's definition in addition to the table-specific columns below.

| Column | SQL Data Type | Nullable | Purpose |
| --- | --- | --- | --- |
| `CreatedAtUtc` | `datetime2(7)` | No | Creation timestamp, assigned by the source write process. |
| `ModifiedAtUtc` | `datetime2(7)` | No | Updated on every insert, update, correction, and soft delete; proposed incremental watermark. |
| `IsDeleted` | `bit` | No | Soft-delete indicator; defaults to `0`. |
| `DeletedAtUtc` | `datetime2(7)` | Yes | Deletion timestamp; populated only when `IsDeleted = 1`. |

`ModifiedAtUtc` is maintained by the database write path, not supplied as a clinical event time. Corrections to old events must receive a new modification timestamp. Watermarks alone do not capture physical deletes or guarantee commit ordering; extraction must use the source-consistency and overlap/replay controls in Milestone 5. Physical-delete scenarios require snapshot comparison or supported change capture.

##### Operational Relationships and Validation

- One patient has many encounters, coverages, and appointments. One department and one provider can be referenced by many encounters or events.
- One encounter has many diagnoses, procedures, medication orders, laboratory orders, and vital observations. One medication order has many administration events; one laboratory order has many result components.
- Each appointment links to zero or one encounter; the baseline model permits at most one linked appointment per encounter, enforced by a filtered unique constraint on non-null `Appointment.EncounterID`.
- Require an appointment's patient to match its linked encounter's patient. Child events inherit their patient through the encounter or parent order instead of duplicating patient identifiers.
- Require end dates/times not to precede start dates/times, death dates not to precede birth dates, and reference bounds to be ordered when both are present. Validate dose/value unit pairs without applying one global clinical range across different units or observation types.
- Enforce positive diagnosis sequences and uniqueness of `(EncounterID, DiagnosisSequence)`; allow at most one active, non-deleted primary diagnosis per encounter.
- Use FK constraints without cascading physical deletes. Normal delete scenarios use soft deletes and an explicit parent/child policy; controlled physical-delete fixtures must preserve referential integrity.
- An encounter has zero or one explicitly assigned primary coverage. Require that coverage to belong to the encounter's patient and include the arrival date within its coverage period. Do not infer primary coverage from an arbitrary patient-level join; secondary coverage and coordination of benefits are outside the baseline scope.
